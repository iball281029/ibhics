รูปแบบ Cluster ที่ผู้ใช้ต้องการ
- ติดตั้งทุกเครื่องเป็น standalone มีเว็บของตัวเองก่อน
- เลือกเครื่องแรกกด Create cluster แล้ว Add เครื่องอื่นเข้ามาทีหลัง
- ไม่มีการ auto-enroll จากการติดตั้งหรืออัปเดต
- เครื่องแรกในงานนี้คือ .104; ห้ามล้างระบบหรือเปลี่ยน Node ID ของเครื่องเดิม
- Membership ปัจจุบันเป็นมุมมองของ manager บน Node1; Node2 ยังมี local web view
  ของตัวเอง ไม่ใช่ระบบ distributed control plane/etcd หรือ manager HA

สิ่งที่ทำเสร็จ
1. Home allocation
   - CPU, RAM, VM disk allocation มีเปอร์เซ็นต์
   - ไม่จำกัดตัวเลขไว้ที่ 100%; เกิน 100% ขึ้นสีแดงพร้อมคำเตือน
   - ผู้ใช้สั่งชัดเจนว่า allocation ไม่ต้องมีกราฟ: คงเป็นตัวเลขเท่านั้น
   - CPU เทียบ hardware threads; allocation disk รวม VM และ template ตามรายละเอียดบน UI
2. กราฟการใช้งานจริง
   - CPU/RAM/storage แยกจาก allocation, แกน Y คงที่ 0–100%, แกนเวลา/หน่วยชัดเจน
   - ประวัติเก็บบน server ที่ /var/lib/ibhics/usage.sqlite3 ของแต่ละ manager
     เปลี่ยน path ได้ด้วย IBHICS_USAGE_FILE
   - background sample ทุก 10 วินาที แม้ไม่มี browser เปิด
   - logout/login หรือ manager restart ไม่ล้างประวัติ
   - เลือก Now (10 นาที), 5 นาที, 30 นาที, 1 วัน, 7 วัน, 30 วัน
   - ช่วงยาวเฉลี่ยเป็นประมาณ 180 จุด; ข้อมูลขาดแสดงเป็น gap/null ไม่แต่งข้อมูล
   - ลบข้อมูลเกิน 30 วันตอนเริ่มระบบและเมื่อเขียน sample
   - CPU รวมแบบถ่วงน้ำหนักด้วย hardware threads, RAM/storage เทียบผลรวม capacity
   - UI แสดงเวลาเริ่มเก็บและพื้นที่เก็บจริง; เริ่มเก็บประมาณ 17:15:40 ของวันนี้
     ไม่สามารถเรียกประวัติก่อนติดตั้งฟีเจอร์นี้ย้อนหลังได้
   - benchmark 259200 จุด/30 วัน ใช้ DB 20512768 bytes = 19.56 MiB
     เผื่อไฟล์ชั่วคราวเป็นราว 25–30 MB ต่อ manager สำหรับรูปแบบข้อมูลนี้
3. ชื่อโหนด
   - display name แยกจาก Node ID และ Linux hostname
   - เก็บ label ใน display_names ของ cluster.json
   - PATCH /api/v1/cluster/nodes/{name} ด้วย display_name
   - ห้ามเปลี่ยน stable ID เพื่อเปลี่ยนชื่อแสดงผล
4. IPMI และสุขภาพอุปกรณ์
   - Nodes/Node Summary แสดง IPMI/BMC เป็นลิงก์
   - Device health แสดง Normal / Warning / Fault reported / Unknown
   - ใช้ local IPMI SDR, Linux EDAC ECC counters และ SMART ของดิสก์
   - อ่านข้อมูลเท่านั้น ไม่รัน SMART self-test, ไม่ reset counter/SEL/config IPMI
   - background collector/cache 60 วินาที ไม่หน่วง normal node summary
   - No reading/slot ว่างเป็น Unknown ไม่ถือว่าเสีย
   - BMC event history แยกจากสถานะปัจจุบัน; วันที่มาจาก clock ของ BMC
5. Create cluster และหน้าจัดการ
   - Admin POST /api/v1/cluster/create สร้าง UUID/name แบบ persistent
   - สร้างจากเครื่องเดี่ยวโดยคงชื่อโหนดและ VM เดิม
   - หน้า #cluster แสดงชื่อ/ID/management node/members/quorum/health/actions
   - Home แสดงชื่อคลัสเตอร์และ Manage cluster link
   - Sidebar และชื่อคลัสเตอร์บน top bar กดมาหน้าจัดการได้
   - หลัง Create จะเปิด Add node; one-node cluster แสดง Single-node cluster
6. Add เครื่องที่ติดตั้งแยกกัน
   - หน้า Cluster ของ standalone มี Node ID, Agent URL, Copy pairing key
   - GET /api/v1/cluster/pairing เฉพาะ admin, Cache-Control: no-store
   - ฝั่ง controller ใส่ Node ID/role/agent URL/pairing key ใน Add node
   - แต่ละโหนดใช้ agent token ของตัวเองได้ ไม่ต้องเปลี่ยนให้เหมือนเครื่องแรก
   - agent_token เป็น SecretStr ใน request; เก็บ per-member key ใน cluster.json
     ด้วย permission 0600; ไม่คืน key ใน normal membership API
   - legacy shared-token agents ยังรองรับ
   - startup installer แบบ standalone เริ่มทั้ง manager และ agent;
     compute agent-only ยังคงเป็น advanced/legacy option

  ไม่ใช่การอ้างว่าระบบตรวจ BIOS สดได้ทุกครั้ง; runtime EDAC อาจเป็นศูนย์
  ขณะที่ BIOS ตัด RAM ช่องเสียออกแล้ว ลบ recorded issue หลังซ่อมและตรวจยืนยันเท่านั้น

- ยังไม่มี automatic VM failover, fencing, distributed storage replication,
  manager failover หรือ etcd membership
- ยังไม่ได้ตั้ง/ทดสอบ cross-host migration transport/certificates/shared storage
  อย่าอ้างว่าเพียงเพิ่มสมาชิกแล้วได้ HA หรือย้าย VM ข้ามเครื่องได้ครบแล้ว
- ตัว UI ของ Node2 ยังเป็น local view; การประสาน local/cluster mutations และ
  single-owner admission ยังไม่มี distributed locking/control plane
